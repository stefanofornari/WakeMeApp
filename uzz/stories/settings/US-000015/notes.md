# Notes — settings/US-000015

* Logic in `LeadTime` (key `notify.leadTimeMinutes`, 1 to 1440, default 5, messages as in the scenarios), tested without JavaFX. A stored value out of range is ignored with a warning, like the Microsoft settings. `--print-config` lists it (`ConfigReport`; the key column is now 22 wide so `notify.leadTimeMinutes` lines up).
* The dialog has a "Notifications" section with a text field (not a Spinner, which clamps silently and cannot say why). Save checks the calendar and the lead time first and saves nothing if either is wrong. Out of range: the message is shown and the field goes back to the nearest limit, as the story says; not a number: the message is shown and the text is kept.
* Apply at once (decision of the scope review): `SettingsListener.leadTimeSaved` makes `CLILauncher` stop the poller and scheduler and poll the same calendar again (`repoll`), so what is scheduled is scheduled again with the new lead time and an already passed trigger fires at once. If the calendar was changed in the same Save only `calendarSaved` is called: it polls the new calendar with the new lead time anyway.
* The lead time of the scheduler comes from the stored setting only (no command-line option). The poll window is now `max(--window, poll interval + lead time)` (`CalendarPoller.effectiveWindow`), so a long lead time still sees its meetings; the check of an explicit `--window` at startup still uses the default 5 minutes.
* The poll interval warning does not block: the value is saved, the dialog stays open showing the warning, and the next Save with nothing changed closes it. The poll interval is a command-line option only, so the warning compares with the one of this run.
* Dependency changed from the canceled scheduler/US-000011 to scheduler/US-000023 (scheduler core and lead time).
* Not verified here: `SettingsDialogTest` and the launcher (JavaFX, TestFX, picocli) need `mvn test`; `LeadTimeTest`, `ConfigReportTest` and `CalendarPollerTest` were run.
