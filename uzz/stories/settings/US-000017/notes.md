# Notes — settings/US-000017

* Key `notify.enabled` (`NotificationsEnabled` in the settings package, on unless stored `false`; listed by `--print-config`). `NotificationSwitch` (notify package) holds the live state in a volatile flag and `guard(...)` wraps the scheduler's trigger: while off it logs "Notification suppressed (globally disabled)" (INFO, no meeting title) and drops the notification. The calendar keeps being polled, so switching on again shows the next meetings at their lead time; one whose trigger fell in the off period is not shown late.
* The guard is applied only when polling a calendar. A single meeting given on the command line (`--title`) is an explicit request and always shows (it would also leave the process waiting for a notification that never comes). Snoozes go through the same scheduler, so a snoozed meeting is held back while off, as the story asks.
* UI: a "Show meeting reminders" check box in the Notifications section; saved with Save like the other fields (decision of the scope review: applies at once on Save, dialog only). `SettingsListener.notificationsSwitched` updates the switch of the running application. Save with only the switch changed does not restart the polling.
* Left out, with scheduler/US-000012 (tray menu): the "Pause Notifications" menu item and the changed tray icon of the scenarios "Disable notifications" / "Menu bar toggle matches settings". The Test Notification button (settings/US-000018) bypasses the switch by design.
