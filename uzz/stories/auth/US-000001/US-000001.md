## auth/US-000001 — Sign In with the Device Code Flow

### User Story

```
AS A User
I WANT to sign in to Microsoft with a code I type in the browser
SO THAT WakeMeApp can read my Outlook calendar without ever seeing my password
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25; MSAL4J (`com.microsoft.azure:msal4j`); tested with MSAL's HTTP client replaced by a stub (see auth/US-000001/notes.md), never against the real service
* **Auth Flow**: OAuth 2.0 Device Authorization Grant (RFC 8628), public client (no secret), through MSAL4J `PublicClientApplication` and `DeviceCodeFlowParameters`
* **Authority**: `https://login.microsoftonline.com/{tenant}/`; `{tenant}` is `organizations` or a tenant id. MSAL does not support `common` or `consumers` for the device code flow (personal Microsoft accounts)
* **Scopes**: `Calendars.Read User.Read`; MSAL adds `offline_access` itself, which is what yields the refresh token

#### Notes
1. Replaces the first draft. The protocol (device code request, polling at the interval, `slow_down`, expiry) is MSAL's, not ours, so it is not specified or tested here beyond one end-to-end path. The failure paths (US-000040), the silent refresh (US-000041), the re-authentication (US-000042) and persistence (US-000002) stay separate stories.
2. Tenant id and client id are parameters of the sign-in; settings/US-000045 and US-000046 provide them.
3. The result is an access token supplier (`Supplier<String>`), the one `GraphCalendarSource` (calendar/US-000003) already takes. Tokens stay in MSAL's in-memory cache here.
4. MSAL gives us a `DeviceCode` (user code, verification URI, message) through a consumer. It is given to an injectable `VerificationPresenter` (implemented in a WebView by auth/US-000049); with no presenter the message is logged at INFO, in MSAL's own words ("To sign in, use a web browser to open the page https://microsoft.com/devicelogin and enter the code ABCD-EFGH").
5. The sign-in runs off the JavaFX thread and does not block the application while the user is at the browser.
6. What to check before implementing (stubbing MSAL's HTTP client, the SLF4J bridge, the dependency footprint) is in `notes.md`.
7. `--calendar` takes a CSV file (a path, as today) or the full address of an Outlook calendar on Microsoft Graph, e.g. `https://graph.microsoft.com/v1.0/me/calendarView` (default calendar) or `https://graph.microsoft.com/v1.0/me/calendars/{calendar-id}/calendarView`. An address makes the application sign in and poll that calendar with `GraphCalendarSource` (calendar/US-000003) and the access token supplier; a file makes it read the file and skip the sign-in. The query (`startDateTime`, `endDateTime`, `$select`, `$orderby`, `$top`) is ours; `/calendarView` is added if the address does not end with it.
8. The access token is only sent to `graph.microsoft.com` over https: any other address is refused at start with a message naming the option, so a wrong address never receives the token. The address of the calendar in the Outlook web app is not an endpoint and is refused the same way.
9. An address needs a client id (stored or `--client-id`); without one the application stops at start with a message saying so.
10. While there is no valid sign-in (before the first one completes, or while a new one is waiting after auth/US-000042) the polling does not read the calendar; it logs a WARNING "waiting for the sign-in" at each poll, as in logging/US-000039, and starts reading as soon as the sign-in completes.
11. Shared calendars of other users (extra scope `Calendars.Read.Shared`) and a short form such as `graph:me` are future items (main scope).

### Acceptance Criteria

```gherkin
Scenario: The device code is shown
  Given a tenant id and a client id
  When the sign-in starts
  Then the device code request carries the client id and the scopes
  And the presenter is asked to show the verification address and the user code

Scenario: The access token is available after the sign-in
  Given the user entered the code and consented
  When the token endpoint answers with an access token
  Then the access token supplier returns that access token

Scenario: The tenant selects the authority
  Given the tenant "organizations"
  When the sign-in starts
  Then the requests go to the endpoints of the tenant "organizations"

Scenario: The presenter fails
  Given a presenter that throws
  When the sign-in starts
  Then the message with the code and the address is still logged
  And the sign-in goes on

Scenario: The calendar is read from Outlook after the sign-in
  Given --calendar is "https://graph.microsoft.com/v1.0/me/calendarView" and the user has signed in
  When the calendar is polled
  Then that calendar is requested with the access token
  And its meetings are scheduled as notifications

Scenario: No polling until the sign-in is done
  Given the sign-in is waiting for the user
  When the poll time comes
  Then the calendar is not read
  And a WARNING says that the application is waiting for the sign-in

Scenario: A file keeps working without a sign-in
  Given --calendar is a CSV file
  When the application starts
  Then the file is read
  And no sign-in is started

Scenario: An address on another host is refused
  Given --calendar is "https://example.com/v1.0/me/calendarView"
  When the application starts
  Then it stops with a message that the calendar address must be on graph.microsoft.com
  And no token is requested or sent

Scenario: An address without a client id
  Given --calendar is a Graph address and no client id is stored or given
  When the application starts
  Then it stops with a message saying that a client id is needed

Scenario: The application is not blocked while waiting
  Given the user has not yet entered the code
  When the sign-in is waiting
  Then the JavaFX thread is free
```
