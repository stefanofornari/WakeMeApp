## auth/US-000042 — Sign In Again When the Refresh Token Is Rejected

### User Story

```
AS A User
I WANT to be asked to sign in again when my saved sign-in no longer works
SO THAT an expired or revoked sign-in is fixed by entering a new code, not by a broken application
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25; MSAL4J (`com.microsoft.azure:msal4j`); tested with MSAL's HTTP client replaced by a stub (see auth/US-000001/notes.md), never against the real service
* **Trigger**: the silent request ends with `MsalInteractionRequiredException` (the refresh token expired, was revoked, or the password changed; the endpoint answered `invalid_grant`)

#### Notes
1. MSAL's cache is emptied and the stored one (auth/US-000002, when it exists) is cleared, then the device code sign-in (auth/US-000001) starts.
2. The user is told with a WARNING in the user's words ("your sign-in expired, sign in again"); the new code is shown as in auth/US-000001.
3. How the calendar polling behaves while there is no valid sign-in is decided by the story that connects the Graph source to the application, not here.

### Acceptance Criteria

```gherkin
Scenario: A rejected refresh token starts a new sign-in
  Given a refresh token that Microsoft no longer accepts
  When a silent request ends with interaction required
  Then the cached and the stored sign-in are cleared
  And a WARNING tells that the sign-in expired
  And the device code sign-in is started

Scenario: The new sign-in replaces the old one
  Given the user completes the new sign-in
  When the tokens are received
  Then the access token supplier returns the new access token
  And the new sign-in is the one stored
```
