## auth/US-000002 — Token Storage and Refresh

### User Story

```
AS A User
I WANT my authentication tokens stored securely and refreshed automatically
SO THAT I don't need to re-authenticate on every app launch
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25
* **Storage**: Encrypted file in platform-appropriate config directory (`~/Library/Application Support/WakeMeUp/` on macOS)
* **Encryption**: AES-256-GCM with key derived from system keystore / Keychain
* **Token Lifetime**: Access token ~1 hour, Refresh token ~90 days (Microsoft default)

#### Notes
1. Use platform keystore: macOS Keychain, Windows DPAPI, Linux Secret Service
2. Fallback to PBKDF2-derived key from user password if keystore unavailable
3. Automatic refresh when access token expires (proactive: 5 min before expiry)
4. Handle revoked/expired refresh token → trigger re-authentication flow

### Acceptance Criteria

```gherkin
Scenario: Tokens persisted and loaded on restart
  Given the user has completed authentication (auth/US-000001)
  When the app is closed and reopened
  Then the refresh token is retrieved from secure storage
  And a new access token is obtained without user interaction
  And calendar polling begins immediately

Scenario: Access token refreshed proactively before expiry
  Given a valid access token with 5 minutes remaining
  When the token refresh threshold is reached
  Then a new access token is requested using the refresh token
  And the new tokens replace the old ones in secure storage
  And calendar polling continues uninterrupted

Scenario: Expired refresh token triggers re-authentication
  Given the refresh token has expired or been revoked
  When the app attempts to refresh the access token
  And the token endpoint returns invalid_grant
  Then the stored tokens are cleared
  And the Device Code Flow (auth/US-000001) is initiated automatically
  And the user is prompted to re-authenticate

Scenario: Secure storage protects tokens at rest
  Given tokens are stored in the config directory
  When an unauthorized process attempts to read the token file
  Then the file contents are encrypted and unreadable
  And the encryption key is not stored alongside the file
```
