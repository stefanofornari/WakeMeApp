## auth/US-000002 — Remember the Sign-In Across Restarts

### User Story

```
AS A User
I WANT to be still signed in when I restart the application
SO THAT I do not have to enter a code every time it starts
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25; HTTP with the JDK `HttpClient`, JSON with org.json; tested against stubbed HTTP (xtest, see `uzz/library/HOWTO StubHttpClient.md`), never against the real service
* **Storage**: a file in the application data folder (directories-jvm, as the log), readable and writable by the owner only (POSIX permissions where the platform has them)
* **Token lifetime**: access token about 1 hour, refresh token about 90 days (Microsoft defaults)

#### Notes
1. Replaces the first draft of this story (storage and refresh together): the refresh is auth/US-000041, the revoked token is auth/US-000042.
2. Behind a `TokenStore` interface (load, save, clear) so that another store (a system password manager, for instance, which is out of scope for now) can replace the file store later without touching the sign-in.
3. Only the refresh token and the account hint are stored; the access token is short-lived and obtained again.
4. The file is stored in the clear, protected only by owner-only permissions; encryption and system password managers (Keychain, DPAPI, libsecret) are out of scope for now.
5. A store that cannot be read or understood is treated as empty, with a WARNING; the user simply signs in again.

### Acceptance Criteria

```gherkin
Scenario: The sign-in is stored
  Given the user has signed in
  When the refresh token is received
  Then it is saved in the token file of the application data folder
  And the file can be read and written by its owner only

Scenario: A stored sign-in is used at start
  Given a refresh token is stored
  When the application starts
  Then a new access token is obtained with it, without opening the browser
  And the calendar polling can begin

Scenario: A refreshed token replaces the stored one
  Given a refresh token is stored
  When the token endpoint answers a refresh with a new refresh token
  Then the stored refresh token is replaced

Scenario: No stored sign-in
  Given there is no token file
  When the application starts
  Then the device code sign-in is started

Scenario: The token file cannot be used
  Given the token file is not readable as tokens
  When the application starts
  Then a WARNING says that the saved sign-in was ignored
  And the device code sign-in is started
```
