## auth/US-000002 — Remember the Sign-In Across Restarts

### User Story

```
AS A User
I WANT to be still signed in when I restart the application
SO THAT I do not have to enter a code every time it starts
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25; MSAL4J (`com.microsoft.azure:msal4j`); tested with MSAL's HTTP client replaced by a stub (see auth/US-000001/notes.md), never against the real service
* **Storage**: a file in the application data folder (directories-jvm, as the log), readable and writable by the owner only (POSIX permissions where the platform has them)
* **Persistence hook**: MSAL4J `ITokenCacheAccessAspect` (`beforeCacheAccess` loads, `afterCacheAccess` saves), with the cache serialized by MSAL (`serialize()` / `deserialize()`)

#### Notes
1. Replaces the first draft of this story: the silent renewal is auth/US-000041, the rejected sign-in is auth/US-000042.
2. Behind a `TokenStore` interface (load, save, clear, as text) so that another store (a system password manager, for instance, which is out of scope for now) can replace the file store later without touching the sign-in.
3. The stored text is MSAL's serialized cache: accounts, access, refresh and id tokens. We do not read or write its content ourselves.
4. The file is stored in the clear, protected only by owner-only permissions; encryption and system password managers (Keychain, DPAPI, libsecret) are out of scope for now.
5. A store that cannot be read or understood is treated as empty, with a WARNING; the user simply signs in again.
6. A save is written to a temporary file and moved over the old one, so a crash does not leave a half-written file.

### Acceptance Criteria

```gherkin
Scenario: The sign-in is stored
  Given the user has signed in
  When MSAL has updated its cache
  Then the serialized cache is saved in the token file of the application data folder
  And the file can be read and written by its owner only

Scenario: A stored sign-in is used at start
  Given a token file with a valid sign-in
  When the application starts
  Then an access token is obtained silently
  And the presenter is not asked to show anything
  And the calendar polling can begin

Scenario: A renewed token replaces the stored one
  Given a token file with a sign-in
  When MSAL renews the tokens
  Then the token file holds the renewed cache

Scenario: No stored sign-in
  Given there is no token file
  When the application starts
  Then the device code sign-in is started

Scenario: The token file cannot be used
  Given the token file is not readable as a cache
  When the application starts
  Then a WARNING says that the saved sign-in was ignored
  And the device code sign-in is started

Scenario: A crash during a save keeps the old file
  Given a token file with a sign-in
  When writing the new content fails half way
  Then the old token file is unchanged
```
