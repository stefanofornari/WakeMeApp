## auth/US-000041 — Refresh the Access Token Silently

### User Story

```
AS A User
I WANT the access token to be renewed before it expires
SO THAT the calendar polling is never interrupted by an expired token
```

#### Status
DONE

#### Dependencies
- auth/US-000001

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25; MSAL4J (`com.microsoft.azure:msal4j`); tested with MSAL's HTTP client replaced by a stub (see auth/US-000001/notes.md), never against the real service
* **Call**: `acquireTokenSilently` with the cached account; MSAL answers from its cache or uses the refresh token when the access token is expired

#### Notes
1. The access token supplier given to `GraphCalendarSource` (calendar/US-000003) asks MSAL silently each time it is called; the decision to renew is MSAL's, there is no threshold of ours.
2. One silent request at a time, whatever the number of callers.
3. The renewed tokens stay in MSAL's cache (and in the store once auth/US-000002 exists).
4. After a server error (5xx) or a 429, MSAL itself does not send the same request again for 5 seconds (or for the `Retry-After` Microsoft gives); during that time the supplier treats the answer as a temporary failure too. Its throttling is static, shared by all instances of the application in the JVM, so tests use a client id of their own.
5. A silent request that fails for a temporary reason (network, 5xx, 429) returns the current token if it is still valid, logs a WARNING and is tried again at the next call; if the token is no longer valid the supplier fails with a temporary calendar access error. A rejected sign-in is auth/US-000042.

### Acceptance Criteria

```gherkin
Scenario: A valid token is used as it is
  Given a cached access token that is far from its expiry
  When the supplier is asked for the token
  Then the same token is returned
  And no request is sent

Scenario: An expired token is renewed
  Given a cached access token that expired and a refresh token
  When the supplier is asked for the token
  Then a refresh request is sent to the token endpoint
  And the new access token is returned

Scenario: Callers asking at the same time cause one request
  Given an access token that needs to be renewed
  When two callers ask for the token at the same time
  Then only one refresh request is sent
  And both get the new token

Scenario: A temporary failure does not lose the sign-in
  Given an access token that is still valid and close to its expiry
  When the renewal fails because the server answers 503
  Then the current token is still returned
  And a WARNING is logged
  And the renewal is tried again at a next call, once MSAL's back-off is over

Scenario: A temporary failure with an expired token
  Given an access token that expired
  When the renewal fails because the network is down
  Then the supplier fails with a temporary calendar access error
  And a WARNING is logged
```
