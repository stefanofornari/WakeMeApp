## auth/US-000041 — Refresh the Access Token Silently

### User Story

```
AS A User
I WANT the access token to be renewed before it expires
SO THAT the calendar polling is never interrupted by an expired token
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25; HTTP with the JDK `HttpClient`, JSON with org.json; tested against stubbed HTTP (xtest, see `uzz/library/HOWTO StubHttpClient.md`), never against the real service
* **Grant**: `refresh_token`, same token endpoint and scopes as the sign-in
* **Threshold**: 5 minutes before the expiry

#### Notes
1. The access token supplier given to `GraphCalendarSource` (calendar/US-000003) always returns a token that is valid for at least the threshold: when the current one is closer to its expiry it is renewed before being returned.
2. One refresh at a time, whatever the number of callers.
3. The new refresh token returned by Microsoft replaces the old one (in memory, and in the store once auth/US-000002 exists).
4. A refresh that fails for a temporary reason (network, 5xx, 429) keeps the current token while it is still valid, logs a WARNING and is tried again at the next request; `invalid_grant` is auth/US-000042.

### Acceptance Criteria

```gherkin
Scenario: A token far from its expiry is used as it is
  Given an access token that expires in 40 minutes
  When the supplier is asked for the token
  Then the same token is returned
  And no request is sent

Scenario: A token close to its expiry is renewed first
  Given an access token that expires in 4 minutes and a refresh token
  When the supplier is asked for the token
  Then a refresh request is sent to the token endpoint
  And the new access token is returned
  And the new expiry time and refresh token are kept

Scenario: Callers asking at the same time cause one refresh
  Given an access token that needs to be renewed
  When two callers ask for the token at the same time
  Then only one refresh request is sent
  And both get the new token

Scenario: A temporary failure does not lose the sign-in
  Given an access token that expires in 4 minutes
  When the refresh fails because the server answers 503
  Then the current token is still returned
  And a WARNING is logged
  And the refresh is tried again at the next request
```
