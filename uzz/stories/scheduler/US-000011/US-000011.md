## scheduler/US-000011 — Background Scheduler for Automatic Notifications

### User Story

```
AS A User
I WANT the app to run in the background and notify me automatically when meetings are about to start
SO THAT I don't need to keep the app window open to receive notifications
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25
* **Scheduler**: `ScheduledExecutorService` with single thread
* **Poll Interval**: Configurable (default 5 min, settings/US-000015)
* **Lead Time**: Configurable (default 5 min, settings/US-000015)
* **Notification Timing**: Trigger at `meetingStart.minusMinutes(leadTime)`
* **Snooze Handling**: Separate scheduled tasks for each snooze
* **Thread Safety**: All UI updates via `Platform.runLater()`
* **Lifecycle**: Start on app launch, shutdown on app exit
* **Process Model**: Long-lived JVM process (not launchd/cron periodic) — managed by platform launcher (Launch Agent on macOS, Registry Run on Windows, systemd user service on Linux)

#### Notes
1. **Architecture Decision**: The app runs as a single long-lived background process. The platform-specific launcher (Launch Agent / Registry Run / systemd user service) starts the JVM at login and keeps it alive. The JVM's internal `ScheduledExecutorService` handles all polling, notification scheduling, and snooze management. This avoids JVM startup latency (~2-5s) that would cause missed notifications with periodic launchd/cron jobs, and preserves in-memory state (pending notifications, active snoozes) across polls.
2. Runs in background even when main window is hidden
3. Coordinates with Graph polling (can share poll results)
4. Handles system sleep/wake (reschedule on wake) — platform-specific listeners: `NSWorkspaceDidWakeNotification` (macOS), `WM_POWERBROADCAST` (Windows), `logind` DBUS `PrepareForSleep` (Linux)
5. Persists pending notifications to survive restart (local file: next-trigger timestamps + meeting IDs)
6. Timezone-aware: all calculations in user's local timezone
7. Platform launcher integration: packaging.macos/US-000019, packaging.windows/US-000020, packaging.linux/US-000021

### Acceptance Criteria

```gherkin
Scenario: User receives notification automatically without keeping app open
  Given a meeting starts at 10:00 AM
  And lead time is set to 5 minutes
  And the app is running in the background (window hidden, menu bar only)
  When the system time reaches 9:55 AM
  Then the notification engine is triggered for this meeting
  And the full-screen overlay appears (notify/US-000005)
  And the user is notified without having the app window open

Scenario: Multiple meetings are handled correctly
  Given meetings at 10:00 AM and 10:30 AM
  And lead time is 5 minutes
  And the app is running in the background
  When the scheduler runs
  Then notifications are scheduled for 9:55 AM and 10:25 AM
  And both trigger independently
  And the user receives both notifications at the correct times

Scenario: Scheduler integrates with calendar polling
  Given the poll interval is 5 minutes
  When the scheduler wakes for polling
  Then it fetches events for the next (leadTime + pollInterval + buffer) window
  And updates the notification schedule based on current calendar state
  And adds new meetings, removes cancelled ones, updates changed ones
  And the user's notification schedule stays in sync with their calendar

Scenario: Notifications still work after system sleep/wake
  Given a notification is scheduled for 9:55 AM
  And the system sleeps at 9:50 AM and wakes at 9:56 AM
  When the system wakes
  Then the scheduler detects the missed notification
  And triggers it immediately (within 10 seconds of wake)
  And the overlay appears with correct countdown
  And the user doesn't miss the notification due to system sleep

Scenario: Scheduled notifications survive app restart
  Given notifications are scheduled for 9:55 AM and 10:25 AM
  And the user quits the app at 9:50 AM
  When the user restarts the app at 9:52 AM
  Then the scheduler restores both pending notifications
  And the 9:55 AM notification triggers on time
  And the 10:25 AM notification remains scheduled
  And the user doesn't miss notifications due to app restart

Scenario: User can disable notifications globally
  Given the user has disabled notifications in settings (settings/US-000017)
  When the scheduler would trigger a notification
  Then no notification is shown
  And the meeting is logged as "skipped (notifications disabled)"
  And the user's preference to not be disturbed is respected
```
