## logging/US-000037 — Log the Main Flows at the Right Level

### User Story

```
AS A User
I WANT the application to log what it does at levels that mean something
SO THAT I can read the log and tell what happened, and what needs my attention
```

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25
* **Levels**: ERROR (`SEVERE`) only what the user MUST know; WARN (`WARNING`) what a user understands and should care about; INFO main flows, mostly happy path, worded for the user; DEBUG (`FINE`) detail for investigating
* **Scope**: all messages the application writes today with `System.out`/`System.err` and every existing log call; the output of picocli (help, version, invalid arguments) is not logging

#### Notes
1. Document the level policy in `uzz/project/development_framework.md` (Logging section).
2. Starting points: `CLILauncher` prints the raw and processed arguments (DEBUG), "Scheduled ... for ..." and "Polling ..." (INFO), "Showing overlay for ..." with start, end and URL (DEBUG for the details; INFO that a notification is shown), "Press Ctrl+C ..." hints (console only, not logged); the scheduler logs a failing handler at SEVERE (ERROR); the poller logs a failed poll at WARNING; the calendar source warns that its file is missing.
3. Also INFO: application start (with the options in use), snooze chosen, notification dismissed, snoozed notification due, meeting rescheduled or cancelled after a calendar change, shutdown.
4. Messages are written for the user: no class names, no internal ids except the calendar event id where it helps.

### Acceptance Criteria

```gherkin
Scenario: The main flow of a scheduled meeting can be followed in the log
  Given the application runs on a calendar file with a meeting starting in 12 minutes
  When the meeting is scheduled, shown, snoozed once and dismissed
  Then the log, at INFO, tells in order: polling started, the meeting scheduled for its time, the notification shown, the snooze and when it ends, the notification shown again, the dismissal

Scenario: Detail is only logged with --debug
  When the overlay is shown
  Then the start, end and join URL of the meeting are logged at DEBUG
  And not at INFO

Scenario: A calendar change is logged
  Given a meeting is scheduled
  When it is moved in the calendar
  Then an INFO message says it was rescheduled, with the new time

Scenario: Problems are logged at the level of their consequence
  When the calendar file is missing
  Then a WARN message names the file
  When a notification cannot be shown because of an unexpected failure
  Then an ERROR message is logged

Scenario: Nothing is written with System.out for logging purposes
  Then no log message of the application is written with System.out or System.err
```
