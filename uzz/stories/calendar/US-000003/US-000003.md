## calendar/US-000003 — Microsoft Graph Calendar Source

### User Story

```
AS A User
I WANT the app to read my Outlook/Teams meetings from Microsoft Graph
SO THAT my notifications are based on my real calendar
```

#### Status
WIP

#### Dependencies
- calendar/US-000028
- an access token, given as a supplier: how it is obtained is up to the auth stories (auth/US-000001, auth/US-000002), not needed to build or test this one

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25
* **Role**: the Microsoft Graph implementation of the calendar-source interface of calendar/US-000028; when and how often it is called, which meetings are eligible and how changes reach the scheduler are decided by calendar/US-000028, calendar/US-000029 and scheduler/US-000030
* **Endpoint**: `GET /me/calendar/events` (or `calendarView`) with `$filter=start/dateTime ge {from} and start/dateTime lt {to}`, `from` and `to` being the window requested by the poller
* **Pagination**: Handle `@odata.nextLink` for large result sets
* **Rate Limits**: Respect `Retry-After` headers, implement exponential backoff
* **HTTP Client**: JDK HttpClient, tested against stubs (see development framework)

#### Notes
1. Called from the poller's background thread, never from the JavaFX Application Thread
2. Map each Graph event to the meeting data of calendar/US-000004 (event id, title, start/end, join URL, organizer, response status, all-day flag) without filtering: eligibility is calendar/US-000029
3. Handle timezone correctly (convert to the user's local time)
4. A failure is reported to the poller by throwing; the poller logs it and tries again at the next poll (calendar/US-000028)
5. Removed from the previous version of this story: poll interval, query window, caching and "already notified" tracking (now in calendar/US-000028 and scheduler/US-000030) and "only online meetings" (a matter for calendar/US-000029)

### Acceptance Criteria

```gherkin
Scenario: Meetings starting in the requested window are returned
  Given the user is authenticated with a valid access token
  And the calendar has a meeting starting in 12 minutes and one starting in 2 hours
  When the source is asked for the meetings starting in the next 15 minutes
  Then a GET request is made to the Graph events endpoint with the matching $filter
  And only the meeting starting in 12 minutes is returned, with its event id, title, times, join URL, organizer and response status

Scenario: Pagination is followed until all events are retrieved
  Given the response contains an @odata.nextLink
  When the source reads the events
  Then subsequent requests follow the nextLink until it is absent
  And all events are returned as a single list

Scenario: Rate limiting is respected
  Given the Graph API returns a 429 status with a Retry-After header
  When the source receives the response
  Then it waits for the specified duration before retrying
  And uses exponential backoff on subsequent 429s

Scenario: Network errors are reported to the caller
  Given a network error occurs (timeout, DNS, connection refused)
  When the source reads the events
  Then the failure is thrown to the caller
  And no partial result is returned

Scenario: Times are converted to the user's timezone
  Given events are returned in UTC
  And the system timezone is America/Los_Angeles
  When the events are mapped
  Then start and end times are in local time
```
