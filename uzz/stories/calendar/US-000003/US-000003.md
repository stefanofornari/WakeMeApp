## calendar/US-000003 — Poll Calendar Events for Timely Notifications

### User Story

```
AS A User
I WANT the app to regularly check my Outlook/Teams calendar for upcoming meetings
SO THAT I receive notifications at the right time without manually refreshing
```

TODO

#### Dependencies
- auth/US-000002

#### Technical Context & Constraints
* **Target System**: JavaFX desktop app (macOS primary)
* **Toolchain / Rules**: Maven + JavaFX 25 + Java 25
* **Endpoint**: `GET /me/calendar/events` with `$filter=start/dateTime ge {now} and end/dateTime le {now+window}`
* **Default Poll Interval**: 5 minutes (configurable via settings/US-000015)
* **Query Window**: Lead time + buffer (default: lead time + 10 minutes)
* **Pagination**: Handle `@odata.nextLink` for large result sets
* **Rate Limits**: Respect `Retry-After` headers, implement exponential backoff

#### Notes
1. Run in background thread, not on JavaFX Application Thread
2. Cache events locally to avoid duplicate notifications
3. Track notified events to prevent re-notification on subsequent polls
4. Handle timezone correctly (convert to user's local time)
5. Only fetch events where `isOnlineMeeting` is true or has join URL

### Acceptance Criteria

```gherkin
Scenario: User receives timely notifications because app polls calendar regularly
  Given the user is authenticated with valid access token
  And a meeting starts in 3 minutes (within lead time window)
  When the poll interval elapses and the scheduler triggers a calendar poll
  Then a GET request is made to /me/calendar/events with appropriate $filter
  And the meeting is returned in the response
  And the notification engine evaluates and triggers the notification
  And the user sees the full-screen overlay at the correct lead time

Scenario: Poll handles pagination correctly for users with many meetings
  Given the user's calendar has more events than the page size (default 100)
  When the poll request returns an @odata.nextLink
  Then subsequent requests follow the nextLink until all events are retrieved
  And all events are combined into a single result set
  And no meetings are missed due to pagination

Scenario: Poll respects rate limits without user impact
  Given the Graph API returns a 429 status with Retry-After header
  When the poll receives the rate limit response
  Then the scheduler waits for the specified Retry-After duration
  And then retries the request with exponential backoff on subsequent 429s
  And the user's notifications are not affected (may be slightly delayed)

Scenario: Poll handles network errors gracefully
  Given a network error occurs during polling (timeout, DNS, connection refused)
  When the poll request fails
  Then the error is logged
  And the scheduler schedules the next poll at the normal interval
  And the user's existing scheduled notifications still trigger on time

Scenario: Timezone conversion ensures correct notification timing
  Given events are returned in UTC from Graph API
  And the user's system timezone is set to a specific zone (e.g., America/Los_Angeles)
  When events are processed
  Then start/end times are converted to the user's local timezone
  And the lead time calculation uses local time
  And the user receives notifications at the correct local time
```
